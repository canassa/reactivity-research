## Done

- `frameworks/elm/`: elm 0.19.1-6 (npm installer), uglify-js 3.19.3, Elm packages pinned in
  `template/elm.json` (browser 1.0.2, core 1.0.5, html 1.0.1, json 1.1.4, regex 1.0.0, and
  time, url, virtual-dom 1.0.5 indirect). `npm ci` pre-fetches the packages into

## Learned

- **Elm writes no source maps.** The build writes one for `elm make`'s output: each top-level
  declaration is named after its origin (`$author$project$…`, `$elm$core$…`, `_Kernel_…`).
  uglify-js composes that map through both passes. Kernel code it inlines into app functions
  (tuples' `{a:…,b:…}`) stays attributed to the kernel, so the runtime grows by a few dozen
  bytes with N.
- **Rendering timing:** a message redraws on the next animation frame, except handlers that
  stop propagation (`onInput`), which redraw at once. That is Elm's fix for the caret problem
  of controlled inputs. The custom number-input decoder stops propagation for the same reason.
  `settled()` waits two frames: one for the redraw, one for the extra frame Elm asks for
  afterwards, so none is pending when dispose is checked.
- **Disposal without an unmount API is clean in practice.** `Browser.element` adds listeners
  only to its own nodes, and it creates no timers. Removing the nodes and dropping the program
  leaves 0 listeners and 0 timers. A second `init` works.
- **uglify-js 3.19 defaults to `module: true`** (also from the CLI). Elm's
  `(function(scope){…}(this))` wrapper survives it.
- **npm now gates dependency install scripts.** The `elm` package's hard-link script is
  skipped. That is harmless, because the build runs the `@elm_binaries` binary directly.
- Elm's slope is mostly `Main`'s per-widget wiring: the config record, a model field, a `Msg`
  constructor, and branches in `update`, the two decoders and `view`. Its runtime stays near
  7 KB br.
