# 2026-10-16: CPU time per event (`./rr bench`)

The project measured size only; `./rr work` counts calls but not time. This session built
`./rr bench`: script time of one event, and of startup, against N, from Chrome traces. The method
is in `harness/bench/README.md`.

## What was built

- `harness/bench.js` (the command), `harness/bench/lib/` (trace timing, statistics, the driver,
  shared do/undo pairs) and one module per scenario that turns `./rr work`'s actions into
  repeatable do/undo pairs on the same targets. `./rr work` itself is unchanged.
- The timing rule is js-framework-benchmark's (`timeline.ts`, via beni's `trace.mjs`), applied
  per rep between two user-timing marks of one long trace. The protocol is not theirs: one page per
  app and session, real CDP input, no throttling, 10–40 reps until the median's bootstrap interval
  is within ±3%.
- A correctness gate (./rr check's script check, now exported from `check.js`), sessions with the
  framework order reversed, load recorded and enforced, `--aa`, `--remote`, a `"$bench"` block in
  `runs.json` (a `$` key, because `./rr report` treats every other key as an emitter), and a CPU
  card per scenario on the plots page.

## What was learned

- **A CDP `Runtime.evaluate` is an `EvaluateScript` in the trace**, so any harness call inside a
  rep's window is timed. The driver writes the end mark after a passive 40 ms wait and only then
  calls `rr.settled()`; neither the harness nor the adapter is ever timed.
- **Microtask renders (beni-tea) appear as `FunctionCall`s inside the click's EventDispatch;**
  Elm's rAF render is a `FireAnimationFrame` a frame later, and Elm's extra rAF after a render
  falls inside the window too, as it would in js-framework-benchmark (Elm clicks: total ≈ 31 ms,
  two frames).
- **beni's controlled checkboxes fire a no-op zero-delay timer after the commit,** so no commit
  follows the last event. timeline.ts then takes the last commit; the port first lacked that
  fallback and dropped those reps. Samples that use it carry `lastCommit: true`.
- **Rotating and reversing the order every session is a no-op for two frameworks**: the first A/A
  run measured the same app first in both sessions (2–5% higher both times). Fixed: reverse on even
  sessions, rotate every other session.
- **Typed input:** `Input.insertText` gives beforeinput/textInput/input; Backspace through
  `Input.dispatchKeyEvent` gives keydown with the input inside it; ArrowDown on a focused
  `<select>` changes it in headless Linux Chrome.

## Numbers (this machine: dagon, Ryzen 9 5950X, shared, load 1.1–2.5; rough)

`--quick` (5 reps), N=16, seed 1, median script µs over the local events: tea-inline 62,
digest 64, tea-local 68, tea-dirtybits 70, Solid 103, beni-tea 117, beni-direct 146, Elm 345
(shared-components). unique-components N=16→256 growth of the median local event: Solid 1.02×,
tea-inline 1.08×, digest 1.09×, tea-dirtybits 1.12×, tea-local 1.13×, beni-tea 1.32×; Elm 2.25×
from 16 to 64 and 3.5 ms at 256 (its calls grow 4.3× over 16→256).

**A/A** (Solid, shared-components N=16, full method, 2 sessions, order reversed): the two copies'
95% intervals overlap on 26 of 28 halves; median |difference| 3.2%, max 13.6%. The bootstrap
interval is within one page; the copies differ by a few percent between pages, which it does not
see. On this machine about 3–5% is the resolution; a quiet machine should do better.

**Speed:** on this machine every action ran to the 40-rep cap (within-page IQRs ≈ 25%): about
60 s per app per session (shared-components; 7–10 s with `--quick`). The full matrix is 134 apps
× 2 sessions: about 4 hours at that rate, less where reps stop early on a quiet machine.
